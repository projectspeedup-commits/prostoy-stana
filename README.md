# Учёт простоев стана

Простой ввод простоев оборудования: рабочий нажимает «Стан встал» и «Стан пошёл» — по одному нажатию, без вопросов, время ставит система (или вносится задним числом). Причину по классификатору, «что сделали» и брак указывают в конце смены в «Разборе простоев»; там же правится время простоя.

## Как устроено

- `app/core` считает смены, производственные сутки и сводки. Один и тот же код исполняют страница и сервер.
- `app/server` принимает нажатия, хранит базу и отдаёт страницу.
- `app/public` содержит страницу рабочего. Она открывается без сети и досылает нажатия, когда связь вернётся.
- `bridge` передаёт копию данных без фамилий в Google Таблицу.
- `deploy` содержит образцы для запуска в Docker.
- `legacy` хранит исходный скрипт формы, с которого начинался проект.

## Настройки администратора

`GET /api/admin/settings` возвращает расписание двух смен, мастеров (ФИО, смена, телефон), контакты и `refsVersion`. `PUT` принимает `{refsVersion:"версия из GET",settings:{schedule:{shifts:[{no:1,start:"08:00"},{no:2,start:"20:00"}]},people:[],contacts:[]}}`. Конец каждой смены — начало следующей; шаг времени 30 минут, длительность каждой не менее часа. Новый мастер передаётся с пустым `id` или `null`, сервер назначает идентификатор.

Оба запроса требуют ключ устройства `X-Device-Key` с правом администратора (`adminDevices`, в обычном запуске — `STAN_ADMIN_DEVICES`); без права сервер возвращает `403`. Доступность раздела сообщает `canAdmin` в `/api/refs`. Запросы входят в общий лимит ключа: 60 в минуту у `createApp`, 600 в обычном запуске с общей ссылкой. Отдельного пароля администратора пока нет. Ошибки проверки возвращают `400` с русским `message`, тело больше 64 КБ — `413`. При устаревшем или отсутствующем `refsVersion` сервер возвращает `409` с сообщением об изменениях на другом устройстве; форму нужно обновить.

Настройки хранятся в `<STAN_DATA_DIR>/settings.json` (по умолчанию `./data`, в Docker — `/app/data` на постоянном томе). Запись атомарная, предыдущий файл сохраняется в `settings.json.bak`. При наличии настроек они имеют приоритет над `STAN_PEOPLE_FILE`; без файла остаются прежние люди и расписание, телефоны пустые. Новое расписание используется сразу, сохранённые события не переписываются. В `?mock=1` изменения живут в памяти вкладки до перезагрузки.

Повреждённые настройки не останавливают API: используется последний исправный снимок в памяти, затем `settings.json.bak`, затем справочник людей или демо. `/api/health` возвращает `settings: "ok"` или `"fallback"`. Сохранение через администратора восстанавливает основной файл; повреждённая копия сохраняется отдельно и не вытесняет исправный `.bak`.

События принимаются за последние 40 суток; ручной простой — не более 7 суток, брак — 0–1000 тн. Очередь планшета хранится отдельно от квитанций и отправляется по порядку пачками до 50 событий / 40 КБ JSON. Подтверждённые квитанции хранятся до 3 суток и не более 300; связанные ответы и метаданные цепочек сохраняются, пока есть ожидающая или отклонённая запись этого простоя.

Остановка и пуск отправляются отдельно. Их зависимые ответы ждут успешной квитанции. Отклонённый простой показывается одной карточкой со всеми ответами; перенос в чужой простой заполняет только пустые поля. Вкладки объединяют очередь и квитанции через `storage`, окончательные статусы сильнее ожидающих и отклонённых.

Сводка текущей смены в `/api/state` называется `state.summary.shift` (прежнее `summary.day` убрано). Главная, итог смены и `/api/stats` используют общий подсчёт миллисекунд с округлением итога и распределением минут через `apportionMinutes`. Остановки считаются по уникальным `downtimeId`, время после текущего момента не учитывается.

`npm test` включает браузерную проверку, если доступен Chrome (путь можно задать через `STAN_TEST_CHROME`). `node tests/smoke.mjs` запускает отдельный сервер на `127.0.0.1:8299`, проверяет HTTP-сценарии и останавливает его. Данные и снимки — в игнорируемой папке `private` текущего worktree.

## Отчёт в Excel

`GET /api/report.xlsx?from=ГГГГ-ММ-ДД&to=ГГГГ-ММ-ДД` отдаёт книгу .xlsx за производственные сутки (от начала Смены 1, по МСК), обе даты включительно. Нужен ключ устройства `X-Device-Key`. Листы: «Сводка», «По сменам», «Журнал простоев», «Приём и сдача смен»; итоги сводки считает то же ядро, что экран «Показатели стана», время после «сейчас» не считается. Неверный период возвращает `400` с русским `message`: даты корректны, `from` не позже `to`, `to` не позже сегодняшней даты по МСК (ночью, до 08:00, это на день позже текущих суток; время после «сейчас» всё равно не считается), не больше 92 суток. Книгу собирают `app/core/report.js` и `app/core/xlsx.js` (без зависимостей, в Node и в браузере), маршрут — `app/server/report.js`, кнопка и панель периода — `app/public/report-ui.js`. В демо (`?mock=1`, GitHub Pages) отчёт строится в браузере из демо-событий. Интерфейс в настоящем Chrome проверяет `node tests/ui/report-shots.mjs --data <копия данных> --out <папка для снимков>`: свой headless Chrome и сервер на копии данных, раскладка 320–2560 px в обеих темах, скачивание файла, офлайн и демо.

Для второго раунда можно прогнать сценарии на временной копии тестовой базы (PowerShell):

```powershell
$env:STAN_QA_COPY = 'D:\stan-qa-data'
node --test --test-concurrency=1 tests/round2/data.test.js tests/round2/interactions.test.js
Remove-Item Env:STAN_QA_COPY
```

Каждый сценарий копирует базу в `private/round2-data-*`, слушает только `127.0.0.1:8299`, затем закрывает сервер и удаляет свою копию. Исходная база не изменяется. Результаты второго раунда описаны в [отчёте](docs/Второй%20раунд%20исправлений%20QA.md).

## Чего в репозитории нет

Фамилий, ключей, адресов серверов и настроек боевой среды. Они лежат в папке `private` и в файле `.env`, которые в git не попадают.
